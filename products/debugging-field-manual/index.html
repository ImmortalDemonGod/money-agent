The procedure

Every effective debugging session is the same loop, run honestly. When you are lost, you have silently skipped one of these steps. Go back to the one you skipped.

  1. Reproduce it. Reliably, in the smallest environment that still shows it. A bug you cannot reproduce is a bug you cannot verify you fixed.
  2. State the symptom precisely. Write one sentence: what you observed, what you expected, and the exact conditions. Vague symptom, vague search.
  3. Find the last point where the world was correct. Everything between there and the symptom is the search space. Everything else is not.
  4. Bisect the search space. By time (git bisect), by data (half the input), by code path (disable half), or by layer (check the boundary between components). Halving beats staring.
  5. Form ONE hypothesis and design the cheapest test that could prove it false. Not the test that could confirm it — the one that could kill it.
  6. Run the test. Believe the result. If the hypothesis dies, good: the search space just shrank. Go to 5.
  7. Fix it, then re-run the ORIGINAL reproduction from step 1. Then ask: where else does this exact mistake live?

I. Reproduction

1The bug is a gift the moment it reproducesDo not touch anything until you can make it happen twice on demand. The strongest urge — to start fixing — destroys the evidence.
2Shrink the reproduction before you study itDelete half of everything (input, config, code) and check the bug survives. Repeat. Ten minutes of shrinking saves hours of reading, and the minimal case often IS the diagnosis.
3"Intermittent" means you don't control an input yetTiming, ordering, environment, uninitialized memory, external state, randomness seeds, clock. List the inputs you are not controlling; the bug lives in one of them.
4Record everything about the failing run the first timeLogs, core dump, inputs, versions, environment. Flaky failures may not grant a second interview.
5A bug that vanishes when you look at it is telling you the mechanismAdding a print changed timing or memory layout: suspect races and undefined behavior. Attaching a debugger changed scheduling: same. The disappearance is data.

II. Localization

6What changed?Code, data, dependencies, infrastructure, traffic, time. Bugs that appear are usually caused by something that moved. git bisect is the mechanization of this question — use it before your intuition.
7Follow the data, not the codeTrace one concrete value from where it is right to where it is wrong. The bug is at the boundary where correct becomes incorrect. Reading code makes you check what it should do; tracing data shows what it did.
8Check the boundary between yours and theirs firstMost "library bugs" are your call site: wrong argument, violated precondition, ignored return value. Print exactly what crosses the boundary in each direction before blaming the far side.
9The bug is probably not where the error appearsThe crash site is where the corruption was noticed, not where it was created. Ask what upstream actor could have produced this broken state, and how long it survived before detection.
10Binary-search space as well as timeHalf the input file. Half the request payload. Half the feature flags. Any dimension you can halve is a dimension you can bisect.
11Make the system tell you where it diverges from a working oneDiff the logs of a passing and failing run, the environment of a working and broken machine, the output of v1 and v2. Divergence points are search-space boundaries you get for free.
12One failing layer at a timeWhen a full stack misbehaves, test each layer in isolation with the real input: the query alone, the function alone, the endpoint alone via curl. Do not debug two layers simultaneously; you will attribute one layer's bug to the other.

III. Hypotheses

13Say it out loud, to anyone or anythingRubber-duck debugging works because producing an explanation forces serialization of assumptions, and the false one usually sounds false the moment you hear yourself say it.
14Write the three most likely causes before testing anyThe first hypothesis anchors you. Generating three forces the second-most-likely cause into view — which is, embarrassingly often, the actual one.
15Rank by cost-to-test, not by likelihood aloneA 10-second test of an unlikely cause beats a 30-minute test of a likely one. Sort by expected-information-per-minute.
16"That can't be it" is where it isThe bug survives precisely because it lives behind an assumption you refuse to test. List what you are certain of, then verify the cheapest three. Certainty is not evidence; it is untested confidence.
17Never debug on top of a mysteryIf you see something inexplicable on the way to the "real" bug — a warning, an impossible log line, a second oddity — stop. It is usually the same bug wearing different clothes, and always cheaper to understand now.
18The bug count is not one until provenTwo overlapping bugs produce symptoms neither could alone, and every single-cause hypothesis will half-fit. If no hypothesis explains everything, try assuming two causes.

IV. Instrumentation

19Print the thing itself, not your summary of itLog the raw value, with type, length, and quotes around strings: repr(), %q, JSON.stringify. "Looks right" has hidden trailing whitespace, unicode look-alikes, and floats that print rounded.
20Confirm your code is even runningBefore interpreting subtle output: add one unmistakable line at the top and prove the file you are editing is the file that executes. Stale builds, wrong virtualenvs, cached bytecode, and duplicate copies eat entire afternoons.
21Check the actual error message, word by wordRead it aloud, including the part after the colon. The answer is in the message a humiliating fraction of the time, at the exact spot your eyes learned to skip.
22Make the invisible visible at the failure boundaryAssertions at function entry, checksums over data at each pipeline stage, an invariant checker you can call from anywhere. You are building a net that catches the corruption earlier than the crash does.
23A debugger is for reading state, prints are for reading historyUse the debugger when you need to inspect one rich moment; use logging when the question is how state evolved. Choosing the wrong tool for the question wastes the session.
24Timestamps and thread/request IDs on every log lineInterleaved logs without IDs actively lie about causality. With them, most concurrency bugs confess on the first read.

V. The nasty classes

25Race conditions: widen the windowInsert sleeps at suspected interleaving points to make a rare race constant. If a 50ms delay makes it fire every time, you have converted a heisenbug into a regular bug — the hard part is over.
26Memory corruption: the victim is not the culpritWhoever crashed was stabbed by an earlier write. Reach for the tools built for this — ASan, Valgrind, hardware watchpoints on the corrupted address — instead of reading code for the needle.
27Off-by-one: check both ends and the empty caseFirst element, last element, zero elements, exactly-full buffer. Fencepost errors live at boundaries, so test only boundaries: n=0, n=1, n=max, n=max+1.
28Cache bugs: bypass every cache onceHard-refresh, purge CDN, clear memoization, restart the process, SELECT straight from the database. If the symptom changes at any layer, you found which cache is stale — and stale caches masquerade as impossible logic errors.
29Time bugs: distrust every clockTimezones, DST transitions, leap seconds, clock skew between machines, monotonic vs wall clock, midnight rollovers, the 25th hour. If the bug correlates with a date, the bug is the date handling.
30Encoding bugs: look at the bytesHexdump the actual bytes at each hop. UTF-8 vs Latin-1, BOM, CRLF vs LF, NFC vs NFD normalization, URL-encoding applied twice or not at all. Text that "looks identical" routinely isn't.
31Float bugs: equality is the bugAny == between floats, any accumulation across many additions, any currency in floating point. Print full precision (%.17g) before reasoning about values.
32Concurrency deadlock: dump all stacks firstEvery language has a way to dump every thread's stack (jstack, py-spy dump, SIGQUIT). Two threads each holding what the other wants is visible in one screenful — but only if you look at all threads, not the one you suspect.
33Configuration bugs: print the config the process actually loadedNot the file you edited — the values in memory at runtime. Wrong file path, environment override, precedence rules, and deploy lag mean the config you are reading is frequently not the config that is running.
34"Works on my machine": diff the machines, not the vibesVersions (language, libraries, OS), environment variables, locale, filesystem case-sensitivity, network access, data. Enumerate mechanically; the difference is on the list, and intuition is bad at finding it.

VI. When you are stuck

35Re-read the symptom sentence from step 2Half of all lost debugging sessions are solving a drifted version of the problem. Does your current hypothesis still explain the original observation?
36Write down what you know is true, with the evidence for eachThree columns: claim, evidence, confidence. Any claim with an empty evidence cell is a hypothesis you promoted to a fact — demote it and test it.
37Reproduce the OPPOSITECan you make it work correctly on demand? The delta between the smallest failing case and the largest passing case is the bug's silhouette.
38Take the fifteen-minute walkNot folklore: you are stuck in a local minimum of the same three ideas. Distance breaks the loop. The number of bugs solved in the shower is not a coincidence; it is consolidation.
39Explain it to someone junior, in writingA good bug report to a person who knows nothing forces you to state versions, steps, expected, actual — and about a third of the time you never hit send.
40Check the dumb things, out loud, in orderIs it plugged in: right branch, right server, right database, right account, saved file, restarted process, cleared cache. Senior engineers check these FIRST because they are cheap, not because they are likely.
41Read the source of the thing you're blamingThe library, the framework, the standard function. Vendored source, decompiled bytecode, or the docs' fine print. Ten minutes in the actual implementation regularly refutes the model of it you debugged against for an hour.
42Rewrite the suspect ten lines from the specWhen staring cannot find the flaw in a small region, blank it and re-derive it from what it must do. Faster than finding a subtle flaw in the old text, and the diff between versions is often the bug.
43Question the diagnosis of everyone before youTickets arrive pre-diagnosed ("the cache is broken") and the framing is wrong more often than the report. Strip the interpretation, keep the observation, start from the raw symptom.

VII. After the fix

44Explain the mechanism before you accept the fixIf you cannot narrate cause → effect → symptom in one paragraph, you changed the timing, not the truth. "It went away" is remission, not cure, and it will return during a demo.
45Re-run the original reproduction, not a friendly variantThe exact failing case from step 1, unmodified. Fixes have a way of curing the test you wrote while fixing and not the bug you had.
46Hunt the clonesThe same author, the same pattern, the same misunderstanding — grep for the shape of the mistake across the codebase. Bugs are social; they travel in cohorts.
47Add the regression test while the reproduction is warmThe minimal repro from rule 2 is already a test fixture. Committing the fix without it discards the most expensive artifact the session produced.
48Ask what let this bug survive until nowMissing assertion, silent catch block, untested path, log line that lied? Fix the detection gap too, or its siblings will live just as long.
49Write the one-paragraph postmortem in the commitSymptom, mechanism, fix, and how it escaped. Six months from now this paragraph is worth more than the fix, and the discipline of writing it catches wrong fixes today.
50Update your priorsWhatever class this bug belonged to, you will meet it again. The engineers who seem psychic at debugging are running the same procedure as you — with better-calibrated priors, earned one postmortem at a time.
The procedure is the skill. The heuristics are just the procedure, pre-computed for the cases that recur.
